# Intent: Show more than one GitLab host at once

## Problem

The panel shows one GitLab host at a time. Issue #42 asks for several at
once, for example gitlab.com plus a self-managed instance, with "separate
caches, budgets and errors per host, and the host shown on each project
row". #21 fixed data mixing on a host switch (`Polling.resetHost`), which
this builds on.

Today:

- **One host per panel.** `configure()` (`PipelinesPanel.qml` lines
  559-592) reads one `host` string from the plugin's `plugins[]` entry in
  `~/.config/omarchy/shell.json`, defaulting to `gitlab.com`. Changing it
  throws away all data (`Polling.resetHost`), ends every watch, cancels a
  pending action and bumps `hostEpoch`. The README says "One host is shown
  at a time".
- **All polling state is one object for one host.** `Polling.create()`
  holds the repos, details, tasks, the request budget (`starts`), the rate
  cooldown (`cooldown`, `rateFailures`), the auth stop (`auth`, `error`),
  the catalogue error, watches and the merge-request list. A rate limit or
  a logged-out session stops everything.
- **One request at a time.** The panel runs one `gitlab.py` worker at a
  time (`workerBusy`, `PipelinesPanel.qml` lines 627-644); every request
  names the host (`glab api --hostname`, `gitlab.py` `request`).
- **Project identity is the path alone.** Rows, keys (`Polling.key`),
  `expanded`, `selected`, watches and the merge-request keys use
  `group/project` with no host, so the same path on two hosts would
  collide.
- **Some parts are already per host.** Saved pins are stored per host
  (`gitlab.py` `pins`, `pinned.json` `hosts`). `actions_enabled(host)`
  (`gitlab.py` lines 391-399) checks the entry's host. `Model.browsable`
  only opens links on the panel's host. The open-filter request
  (`menu.py open`, `Model.openFilter`) shows "Repository is on X; this
  panel shows Y" when the repository's remote is on another host.
- **The bar widget's status file names one host** (`Model.barStatus`,
  version 1: `host`, `state`, `running`, `failed`, `countsAt`,
  `cooldownUntil`, `reason`). The widget is installed separately (`bar`
  package), so a newer panel can meet an older widget.
- **nixarchy does not set the host.** Its `gitlab` plugin entry
  (`modules/home.nix`) installs the plugin; users add `host` by hand.

## Proposed outcome

When this is done:

- **Several hosts in one panel.** The plugin's entry can list more than
  one GitLab host. Projects from every host appear in the one list, sorted
  as today (pinned and running first), and each project row shows its host
  when more than one host is configured. A config with only `host`, or
  with nothing, works exactly as today.
- **Hosts are independent.** Each host has its own data, request budget,
  rate-limit pause and error. A host that is rate limited, logged out or
  unreachable shows that on its own (in the header or footer and in its
  projects' place) while the other hosts keep updating. Requests still go
  out one at a time, shared fairly between the hosts.
- **The same path on two hosts stays two projects.** Selection, expansion,
  pins, watches, actions, links and merge requests all keep the host with
  the project.
- **Per-host settings.** `actions`, `projects` and `pinned` can be set per
  host. Actions are still off unless turned on for that host.
- **Merge requests from every host** appear in the merge-request view,
  each with its host when more than one is configured.
- **Opening from a repository** (`menu.py open`) filters to the project on
  whichever configured host its remote is on; the notice shows only when
  no configured host matches.
- **The bar widget** adds up running and failed counts across hosts. Its
  tooltip names each host's state, and a host that is stopped or rate
  limited does not hide the others' counts. An older widget still reads
  the status file.
- **Adding or removing a host** in `shell.json` starts or drops only that
  host's data, watches and pending action; the other hosts are untouched.
- The README documents the new config, its limits and what changed.

## Affected users and systems

- Users of the GitLab pipelines panel with more than one GitLab host;
  single-host users must see no change.
- Files: `PipelinesPanel.qml`, `Polling.js`, `PipelinesModel.js`,
  `gitlab.py` (actions and pins per host), `menu.py` (open filter),
  `bar-widget/` (status reading), `README.md`, `manifest.json`, the tests
  (`tests/*.cjs`, `tests/test_*.py`, `tests/qml-smoke.py`).
- Hosts: p620 and razer through the usual release and pin chain. p510 is
  not touched.
- nixarchy needs no change; it does not write the host setting.

## Constraints

- An existing single-`host` or empty config keeps working unchanged,
  including saved pins (stored per host already) and actions opt-in.
- No new background process, daemon, token storage or dependency. `glab`
  stays the only way to reach GitLab, one `--hostname` per request.
- Requests stay paced: no more GitLab load per host than today, and no
  more than one request in flight from the panel at a time.
- A host's data, links and actions never mix with another's: a link opens
  only on its own host, and an action is sent only to the host of the row
  you confirmed.
- The bar widget keeps reading the status file safely across versions in
  both directions (old widget with new panel, new widget with old panel).
- Smoke tests run only in the headless VM check, never on the desktop.

## Open questions

1. **Config shape.** Recommended: a `hosts` list of objects in the same
   plugin entry, each `{"host": "…", "actions": …, "projects": […],
   "pinned": […]}`, used when present; the existing top-level `host`,
   `actions`, `projects` and `pinned` remain the single-host form. The
   alternative, a plain list of host names sharing one `actions`,
   `projects` and `pinned`, is shorter but makes project paths ambiguous.
2. **How many hosts.** Recommended: at most 4; extra entries are ignored
   with a logged warning. Each host adds a catalogue and activity scan.
3. **Sharing the one request slot.** Recommended: round-robin between
   hosts, skipping a host that is paused or stopped, with each host keeping
   today's per-host budget. The alternative, one worker per host in
   parallel, is faster but adds more processes and QML plumbing.
4. **Where the host shows.** Recommended: a short host label on each
   project and merge-request row only when more than one host is
   configured, rather than grouping rows under a host heading, so the
   running-first order stays global.
5. **Bar widget state with a failing host.** Recommended: the widget shows
   the summed counts of the working hosts and a marker (for example the
   stopped colour) only when every host is stopped; one stopped host shows
   in the tooltip. The alternative is to show stopped as soon as any host
   is.
