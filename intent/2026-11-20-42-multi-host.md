# Intent: Show more than one GitLab host at once

## Problem

The panel shows one GitLab host at a time. Issue #42 asks for several at
once, for example gitlab.com plus a self-managed instance, with "separate
caches, budgets and errors per host, and the host shown on each project
row". #21 fixed data mixing on a host switch (`Polling.resetHost`), which
this builds on.

Today:

- **One host per panel.** `configure()` (`PipelinesPanel.qml` lines
  559-596) reads one `host` string from the plugin's `plugins[]` entry in
  `~/.config/omarchy/shell.json`, defaulting to `gitlab.com`. Changing it
  clears the host's polling data (`Polling.resetHost`, which keeps the
  request-start history), ends every watch, discards an unsent action and
  bumps `hostEpoch`. The README says "One host is shown at a time".
- **All polling state is one object for one host.** `Polling.create()`
  holds the repos, details, tasks, the request budget (`starts`), the rate
  cooldown (`cooldown`, `rateFailures`), the auth stop (`auth`, `error`),
  the catalogue error, watches and the merge-request list. A rate limit or
  a logged-out session stops all reads.
- **One read at a time; actions are the exception.** Reads run one
  `gitlab.py` worker at a time (`workerBusy`, `PipelinesPanel.qml` lines
  626-644). Actions run in a separate process (`actionProc`, lines
  387-408) that waits one second after the last request start but can run
  while a read is in flight (README "Actions"). Every request names its
  host (`glab api --hostname`, `gitlab.py` `request`). A request to an
  unreachable host can hold the read slot until its timeout (25 s per
  `glab` call, `gitlab.py` line 123).
- **Nothing carries a host except the panel.** Project rows, keys
  (`Polling.key`: path plus pipeline or job id), `expanded`, `selected`
  and watches use `group/project`; merge-request keys use the numeric
  `project_id!iid` (`Polling.js` line 135), and `jumpMr()` finds the
  project by numeric id (`PipelinesPanel.qml` line 320). The same path or
  id on two hosts would collide. These also use the panel's one `host`:
  job traces (`t`, line 447), watch notices (`Model.watchMessage(e, host,
  host)`, line 196, whose texts name no host), action confirmations
  (`Model.describe`, no host), the actions-off hint, the pins state in QML
  (`configPins`, `savedPins`, `pinsLoadHost`, lines 32-42 and 486-558),
  the merge-request "more on GitLab" row (one dashboard link), the error
  strip (two lines) and `status()` (lines 233-242, one set of counters).
- **Some parts are already per host.** Saved pins are stored per
  lowercased host (`gitlab.py` `pins`). `actions_enabled(host)` (`gitlab.py`
  lines 391-400) re-reads `shell.json` and checks the entry's host.
  `Model.browsable` opens links only on the panel's host. `menu.py open`
  already sends the remote's host with the path; `Model.openFilter` turns
  a mismatch into "Repository is on X; this panel shows Y", but a match
  applies only the path as a text filter. The remote parser drops a URL
  port, and `openFilter` strips the panel's port before comparing.
- **The bar widget's status file names one host** (`Model.barStatus`,
  `version: 1`: `instance`, `host`, `state`, `running`, `failed`,
  `countsAt`, `cooldownUntil`, `reason`, `writtenAt`). The widget accepts
  only version 1, ignores other fields, and hides the counts when the
  state is `stopped`. It is installed separately (`bar` package), so a
  newer panel can meet an older widget.
- **nixarchy does not set the host.** Its `gitlab` plugin entry
  (`modules/home.nix`) installs the plugin; users add `host` by hand.

## Proposed outcome

When this is done:

- **Several hosts in one panel.** The plugin's entry can list more than
  one GitLab host. Projects from every host appear in the one list, sorted
  as today (pinned and running first), and each project and merge-request
  row shows its host when more than one host is configured (also in its
  accessible name and in search). A config with only `host`, or with
  nothing, looks and behaves exactly as today.
- **Hosts are independent.** Each host has its own data, request budget,
  rate-limit pause and error. A host that is rate limited, logged out or
  unreachable says so on its own line, naming the host, and keeps the rows
  it already had; a host that never loaded shows only that line. The other
  hosts keep updating, though a slow host can delay them by up to one
  request timeout at a time.
- **The host goes everywhere the project goes.** Selection, expansion,
  pins, watches, job traces, links, copies, merge-request jumps and
  actions all use the row's own host. Action confirmations, watch notices
  and auth messages name the host when more than one is configured.
- **Per-host settings.** `actions`, `projects` and `pinned` can be set per
  host. Actions stay off for a host unless turned on for that host, and
  the write guard in `gitlab.py` reads the same setting.
- **Merge requests from every host** appear in the merge-request view,
  with a "more on GitLab" row per host that has more than are shown.
- **Opening from a repository** (`menu.py open`) shows that project on
  the configured host its remote is on, not a same-named project on
  another host; the notice shows only when no configured host matches.
- **The bar widget** adds up running and failed counts across hosts. Its
  tooltip names each host's state, and a stopped or paused host does not
  hide the others' counts. The status file stays `version: 1` with its
  current fields, so an older widget still works, and the new widget still
  reads an older panel's file.
- **Adding or removing a host** in `shell.json` starts or drops only that
  host's data, watches and unsent action; a late reply for a removed host
  is ignored, and the other hosts are untouched.
- `status()` reports each host, and the README documents the new config,
  its limits and what changed (including environment tokens, which `glab`
  may send to several hosts).

## Affected users and systems

- Users of the GitLab pipelines panel with more than one GitLab host;
  single-host users must see no change.
- Files: `PipelinesPanel.qml`, `Polling.js`, `PipelinesModel.js`,
  `gitlab.py` (`actions_enabled`), `bar-widget/` (tooltip),
  `README.md`, `manifest.json`, and the tests (`tests/*.cjs`,
  `tests/test_*.py`, `tests/qml-smoke.py`). `menu.py` and the managed
  menu need no change unless the spec finds one.
- Hosts: p620 and razer through the usual release and pin chain. p510 is
  not touched.
- nixarchy needs no change; it does not write the host setting.

## Constraints

- An existing single-`host` or empty config keeps working unchanged,
  including saved pins, the actions opt-in and today's request timing.
- No new background process, daemon, token storage or dependency. `glab`
  stays the only way to reach GitLab, one `--hostname` per request.
- Reads stay one at a time across all hosts, and each host keeps today's
  limits (60 pages a rolling minute, one second between request starts). Actions
  keep today's exception: one at a time, at least one second after the
  last request on their host, possibly alongside a read.
- A host's data, links and actions never mix with another's: a link opens
  only on its own host, and an action is sent only to the host of the row
  you confirmed. A malformed multi-host entry never turns actions on.
- The bar status file stays readable across versions in both directions.
- Smoke tests run only in the VM check (`nix build ./ci#…qml-smoke`),
  never on the desktop.

## Open questions

1. **Config shape.** Recommended: a `hosts` list of objects in the same
   plugin entry, each `{"host": "…", "actions": …, "projects": […],
   "pinned": […]}`. When `hosts` is present and valid it replaces the
   top-level `host`, `actions`, `projects` and `pinned`; duplicate hosts
   (case-insensitive) keep the first. The alternative, a plain list of
   host names sharing one `actions`, `projects` and `pinned`, is shorter
   but makes project paths ambiguous and actions all-or-nothing.
2. **How many hosts.** Recommended: at most 4; extra entries are ignored
   and named in a notice, so they do not look like a discovery failure.
3. **Sharing the read slot.** Recommended: take the most urgent ready
   task across hosts (the open selection first, then refreshes, then
   discovery), round-robin between hosts at the same urgency, and skip
   hosts that are paused or stopped. The alternative, one worker per host
   in parallel, removes the slow-host delay but adds processes and QML
   plumbing.
4. **Where the host shows.** Recommended: a short host label on each
   project and merge-request row only when more than one host is
   configured, rather than grouping rows under a host heading, so the
   running-first order stays global.
5. **Bar widget state with a failing host.** Recommended: the working
   hosts' summed counts stay visible; the widget shows stopped only when
   every host is stopped, and shows the pause when no host is working and
   one is paused. Each host's state is in the tooltip.
6. **Caps across hosts.** Recommended: the 5-watch cap stays for the
   whole panel; the 10-pin cap and the 50 merge requests apply per host.
