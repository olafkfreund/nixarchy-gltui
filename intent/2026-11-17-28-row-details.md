# Intent: Show what GitLab already tells us on each row

## Problem

Pipeline and job rows leave out, or misstate, information the panel already
has or can get without extra requests:

- **Merge-request refs are raw.** A merge-request pipeline's `ref` is
  `refs/merge-requests/123/head`, and the subtitle prints it as is
  (`PipelinesModel.js:139`, `head_branch` from `gitlab.py:150`). The user has
  to read the number out of a long path.
- **Durations freeze between polls.** `duration(item, now)`
  (`PipelinesModel.js:71-77`) runs only when rows are rebuilt, which happens on
  a poll reply or a key press (`PipelinesPanel.qml:113`). The panel ticks
  `now` every second (`:287`), but nothing rebuilds the rows on that tick. So a
  running job's time stands still, then jumps.
- **A finished row says how long it took, not when it ended.** There is no
  "finished 5m ago", so a green pipeline from this morning looks the same as
  one from a minute ago.
- **Failure reasons are dropped.** GitLab's job list sends `failure_reason`,
  for example `script_failure`, `runner_system_failure` or
  `stuck_or_timeout_failure`. The helper does not pass it on (`job()`,
  `gitlab.py:158-162`), so a failed job only says "failed".
- **GitLab's own durations are ignored.**
  - The job list sends `duration` and `queued_duration`. The panel recomputes
    the time from timestamps instead, and never shows time spent in the
    queue.
  - Pipelines only get these fields from the single-pipeline endpoint, which
    the panel already calls for some lookups.
- **Freshness is buried.** Only an expanded pipeline shows when its jobs
  were fetched (`PipelinesModel.js:137`), in UTC, inside the subtitle.
  Project rows give no hint of when they were last checked, although the
  poller records it (`r.checked`, `Polling.js:196`).

## Proposed outcome

- **Merge-request pipelines read `!123`.**
  - This covers the refs `refs/merge-requests/123/head`, `…/merge` and
    `…/train`.
  - Branches, tags, detached SHA refs and any other form are shown as today.
  - Searching for `!123` finds the pipeline, and so does the raw ref.
- **Every clock on a row is live** while the panel is open, updating once a
  second:
  - running durations;
  - "finished … ago";
  - project freshness;
  - the pipeline's "jobs fetched … ago".
- **Finished rows show the time since they ended,** for example
  `success · 2m 10s · 5m ago`. This only appears when GitLab gave a real
  finish time (`finished_at`). A row with no finish time does not guess one
  from `updated_at`.
- **A failed job shows why,** for example `failed · script failure`, in
  short readable words, not the raw code.
- **GitLab's job durations are used where they are right:**
  - for a **finished** job, GitLab's `duration` (seconds, including `0`)
    replaces the time computed from timestamps;
  - a **running** job keeps counting up from its start time, so the counter
    never freezes on a snapshot;
  - invalid or missing values fall back to today's computed time;
  - a job that waited in the queue says so, for example `queued 40s`, from
    `queued_duration`.

  Pipeline rows keep today's computed time. GitLab's pipeline list does not
  send durations, and the single-pipeline lookups that do are occasional,
  and are overwritten by the next list reply (`Polling.js:138-143`).
- **Each project row says when it was last checked,** for example
  `0 running · checked 30s ago`.
  - "Checked" means the last poll for that project's running pipelines
    (`r.checked`, `Polling.js:196`). Finished pipelines can be older than
    that, so the wording does not claim the whole list is fresh.
  - The existing states "not checked", "archived", "disabled" and
    "unavailable" stay as they are.
  - The pipeline's "jobs fetched" stamp uses the same relative wording
    instead of a UTC clock time.
- **Tests:**
  - the model tests cover the ref forms, the failure-reason wording, which
    duration is chosen, and the relative times, including the boundaries,
    clock skew and missing times;
  - the smoke test, run in the microVM, checks that a running row's duration
    and a finished row's "ago" change without a poll.

## Affected users and systems

- Files: `gitlab.py` (pass `failure_reason`, `duration` and
  `queued_duration` through), `PipelinesModel.js` (formatting),
  `PipelinesPanel.qml` (live refresh), and the tests: `tests/test_gitlab.py`,
  `tests/model.cjs` and `tests/qml-smoke.py`.
- `Polling.js` is not expected to change.
- It ships through the usual chain to p620 and razer; p510 stays on 1.0.0.

## Constraints

- **No new GitLab requests and no new endpoints.** Only fields already in the
  responses the panel fetches. If a pipeline field needs an extra call, it is
  left out.
- **Rebuilding every second must stay cheap and must not disturb the user:**
  - the selection does not move;
  - the scroll position does not jump;
  - the zoom-settle logic (#22) and the error strip (#26) are unaffected;
  - no binding loop.
- The info column has limited width (35% of the list,
  `PipelinesPanel.qml:486`), so the added text must stay short and elide
  cleanly.
- Server strings stay plain text (`Text.PlainText`). Failure reasons are
  mapped from a known list, and unknown codes are shown with underscores
  replaced.
- Smoke tests run in the microVM only, never on the host desktop.

## Open questions

1. **How to make durations live:**
   - **(a)** rebuild the rows every second while a running row is visible;
   - **(b)** compute the info text in the row delegate from a `now` binding,
     leaving rebuilds as they are.

   I recommend **(b)**: only the time text re-evaluates each second, and the
   list, selection and scroll are not touched. The rows then carry the raw
   times as well as the text, so that the delegate has fresh inputs after
   each poll. The spec will settle the details.
2. **Relative-time wording and limits:** I recommend:
   - `just now` under 10 s;
   - `45s ago` under 1 minute, `5m ago` under 1 hour, `3h ago` under 1 day,
     then `2d ago`, always rounded down;
   - a time in the future (clock skew) reads `just now`;
   - a missing or invalid time is left out.
3. **Where freshness goes on project rows:** I recommend the right-hand info
   column, after the running count (`0 running · checked 30s ago`). The
   subtitle keeps the description. The column already elides; the spec
   checks it at narrow widths and high zoom.

## Review notes

Codex reviewed the draft read-only; agy is out of use (#2748). It confirmed
the display gaps and mapped the helper's requests (`gitlab.py:64-79`). Its
findings, which I checked in the code and folded in above:
- `checked` is the running-pipelines check, not the whole list's
  freshness (`summaryAt` is separate, `Polling.js:275`), so the wording now
  says "checked";
- a server duration must not freeze a running job;
- "ago" needs a real `finished_at`;
- clocks other than the running duration must update too, and the
  delegate needs raw inputs (`syncRows` only compares formatted fields,
  `PipelinesModel.js:169,188`);
- merge-request refs come as `/head`, `/merge` and `/train`, and search
  should find `!N`;
- pipeline durations from single-pipeline lookups are overwritten by list
  merges, so pipelines keep computed times.

Not verified here: the exact GitLab response fields, which come from
Codex's API knowledge and mine, not from a live call. The spec's helper tests
use recorded field names, and the manual check after deploy confirms them.
