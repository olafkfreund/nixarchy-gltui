# Intent: Show what GitLab already tells us on each row

## Problem

Pipeline and job rows leave out, or misstate, information the panel already
has or can get without extra requests:

- **Merge-request refs are raw.** A merge-request pipeline's `ref` is
  `refs/merge-requests/123/head`, and the subtitle prints it as is
  (`PipelinesModel.js:139`, `head_branch` from `gitlab.py:150`). The user has
  to read the number out of a long path.
- **Durations freeze between polls.** `duration(item, now)`
  (`PipelinesModel.js:71-77`) runs only when rows are rebuilt, which happens on
  a poll reply or a key press (`PipelinesPanel.qml:113`). The panel ticks
  `now` every second (`:287`), but nothing rebuilds the rows on that tick. So a
  running job's time stands still, then jumps.
- **A finished row says how long it took, not when it ended.** There is no
  "finished 5m ago", so a green pipeline from this morning looks the same as
  one from a minute ago.
- **Failure reasons are dropped.** GitLab's job list sends `failure_reason`,
  for example `script_failure`, `runner_system_failure` or
  `stuck_or_timeout_failure`. The helper does not pass it on (`job()`,
  `gitlab.py:158-162`), so a failed job only says "failed".
- **GitLab's own durations are ignored.**
  - The job list sends `duration` and `queued_duration`. The panel recomputes
    the time from timestamps instead, and never shows time spent in the
    queue.
  - Pipelines only get these fields from the single-pipeline endpoint, which
    the panel already calls for some lookups.
- **Freshness is buried.** Only an expanded pipeline shows when its jobs
  were fetched (`PipelinesModel.js:137`), in UTC, inside the subtitle.
  Project rows give no hint of how old their pipeline list is, although the
  poller records it (`r.checked`, `Polling.js:196`).

## Proposed outcome

- **Merge-request pipelines read `!123`** wherever the ref is shown. Branches
  and tags are unchanged.
- **Running durations count up live,** once a second, while the panel is
  open.
- **Finished rows show the time since they ended,** for example
  `success · 2m 10s · 5m ago`, in the user's local time terms.
- **A failed job shows why,** for example `failed · script failure`, in
  short readable words, not the raw code.
- **GitLab's durations are used when present:**
  - a job's `duration` is preferred over a time computed from timestamps;
  - a job that waited in the queue says so, for example `queued 40s`.

  Rows without these fields keep today's computed time.
- **Each project row shows how old its data is,** for example
  `checked 30s ago`. The pipeline's "jobs fetched" stamp uses the same
  relative wording instead of a UTC clock time.
- **Tests:**
  - the model tests cover ref shortening, the failure-reason wording,
    duration choice and the relative times;
  - the smoke test, run in the microVM, checks that a running row's duration
    changes without a poll.

## Affected users and systems

- Files: `gitlab.py` (pass `failure_reason`, `duration` and
  `queued_duration` through), `PipelinesModel.js` (formatting),
  `PipelinesPanel.qml` (live refresh), and the tests: `tests/test_gitlab.py`,
  `tests/model.cjs` and `tests/qml-smoke.py`.
- `Polling.js` is not expected to change.
- It ships through the usual chain to p620 and razer; p510 stays on 1.0.0.

## Constraints

- **No new GitLab requests and no new endpoints.** Only fields already in the
  responses the panel fetches. If a pipeline field needs an extra call, it is
  left out.
- **Rebuilding every second must stay cheap and must not disturb the user:**
  - the selection does not move;
  - the scroll position does not jump;
  - the zoom-settle logic (#22) and the error strip (#26) are unaffected;
  - no binding loop.
- The info column has limited width (35% of the list,
  `PipelinesPanel.qml:487`), so the added text must stay short and elide
  cleanly.
- Server strings stay plain text (`Text.PlainText`). Failure reasons are
  mapped from a known list, and unknown codes are shown with underscores
  replaced.
- Smoke tests run in the microVM only, never on the host desktop.

## Open questions

1. **How to make durations live:**
   - **(a)** rebuild the rows every second while a running row is visible;
   - **(b)** compute the info text in the row delegate from a `now` binding,
     leaving rebuilds as they are.

   I recommend **(b)**: only the info text re-evaluates each second, and the
   list, selection and scroll are not touched. The spec will confirm it fits
   the delegate.
2. **Relative-time wording and limits:** I recommend `just now` under 10 s,
   then `45s ago`, `5m ago`, `3h ago`, `2d ago`, rounded down.
3. **Where freshness goes on project rows:** I recommend the right-hand info
   column, after the running count (`0 running · checked 30s ago`). The
   subtitle keeps the description.
