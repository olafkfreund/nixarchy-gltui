# Intent: Show the latest pipeline status on each project row

## Problem

A collapsed project row shows only whether something is running. Its icon
is `●` while a pipeline runs, `✕` when the project itself could not be read,
and `·` otherwise (`PipelinesModel.js:219`). A project whose last pipeline
failed looks the same as one whose last pipeline passed. To find the red
projects the user has to expand each one.

Part of the data is already there, part is not:

- **Known today:** the selected project's ten most recent pipelines (the
  summary's `recent` phase, `gitlab.py:146-148`, run only for the selected
  project, `Polling.js:152`). Runs stay in `r.runs` after the user moves
  away. A pipeline seen running is looked up when it leaves the running
  list, so its final status is known too (`Polling.js:280`).
- **Not known:** for every project that has not been selected and has not
  had a pipeline seen running, the background check reads only the running
  list (`gitlab.py:146`, `status=running`). Their last finished pipeline is
  never fetched.

#35 has just cut background requests (idle checks back off to 60 minutes).
Anything that fetches more for each project works against it.

## Proposed outcome

- Each project row shows the status icon and colour of its latest pipeline
  (✓ passed, ✕ failed, ⊘ cancelled, and so on, the same icons the pipeline
  rows use, `PipelinesModel.js:83-86`) whenever that status is known.
- A running pipeline still shows as running (`●`), and an unreadable project
  still shows its error. Those take precedence over the latest finished
  status.
- A project whose latest status is not known says so in a way that cannot
  be mistaken for passed or failed.
- The row's text says which pipeline the icon describes (for example
  "failed 2 h ago"), so an old result is not read as current.
- The extra request cost, if any, is measured with the #35 scenario
  (`tests/polling.cjs`) and stays within the #35 targets (under 500 requests
  in the first 30 minutes for 137 projects).

## Affected users and systems

- The GitLab pipelines panel: `PipelinesModel.js` (row status and text),
  `PipelinesPanel.qml` (only if the row layout changes), possibly
  `Polling.js` and `gitlab.py` if data has to be fetched.
- `README.md` (the project row description), `manifest.json` (version).
- p620 and razer through the usual deploy chain. p510 is left alone.

## Constraints

- Must not undo #35: no per-project request on every check of every idle
  project unless the scenario shows the targets still hold.
- Must not change what counts as "running" or the pinned/running sort order.
- No new dependency. Reads only through the existing `glab api` helper.
- UI checks run in the microVM, never on the host desktop.

## Open questions

1. **Which pipeline is "latest"?** The newest pipeline on any ref (what
   GitLab's pipelines page lists first), or the newest on the default branch
   (what the project's badge shows)? A failed feature-branch pipeline makes
   the first one red.
2. **Where does the status of never-selected projects come from?**
   a. Show only what is already known (no new requests; most rows stay
      "unknown" until selected or seen running).
   b. Fetch the newest pipeline in the background check (`per_page=1`, one
      more request per check or a changed check).
   c. One GraphQL request per page of projects returning each project's
      latest pipeline status (few requests, but a new API path).
   The spec would pick one; is (a) acceptable as a first step?
3. Should a project whose latest pipeline failed sort higher, after pinned
   and running ones? The issue asks only for the icon; this draft leaves
   the order alone.
