# Intent: Show the latest pipeline status on each project row

## Problem

A collapsed project row shows only whether something is running. Its icon
is `●` while a pipeline runs, `✕` when the project itself could not be read,
and `·` otherwise (`PipelinesModel.js:219`). A project whose last pipeline
failed looks the same as one whose last pipeline passed. To find the red
projects the user has to expand each one.

Part of the data is already there, part is not:

- **Known today:** the selected project's ten most recent pipelines (the
  summary's `recent` phase, `gitlab.py:146-148`, run only for the selected
  project, `Polling.js:152`). Runs stay in `r.runs` after the user moves
  away, bounded to ten completed runs plus kept ones (`Polling.js:259-266`).
  A pipeline seen running is normally looked up after it leaves a complete
  running list, so its final status is known too (`Polling.js:280`); on a
  partial running page it is dropped instead (`Polling.js:273-284`).
- **Not known:** for every project that has not been selected and has not
  had a pipeline seen running, the background check reads only the running
  list (`gitlab.py:146`, `status=running`). Their last finished pipeline is
  never fetched.

#35 has just cut background requests (idle checks back off to 60 minutes).
Anything that fetches more for each project works against it.

## Proposed outcome

- Each project row shows the icon and colour of its **latest known**
  finished pipeline (✓ passed, ✕ failed, ⊘ cancelled, and so on, the same
  icons the pipeline rows use, `PipelinesModel.js:83-86`): the newest
  completed pipeline on any ref among the runs the panel already holds.
- A running pipeline still shows as running (`●`), even if a newer one has
  finished, and an unreadable project still shows its error. Those take
  precedence over the latest finished status.
- The row's text names the pipeline the icon describes and its age, for
  example "last failed 2 h ago", so an old result is not read as current.
  The age comes from `completed_at`, else `updated_at`.
- Three cases stay distinct: never checked ("not checked", `·`), checked
  with no pipelines ("no pipelines", `·`), and checked with no finished
  pipeline known (`·`, running count only).
- No new requests. The #35 scenario (`tests/polling.cjs`) is unchanged:
  471 requests in 30 minutes, background checks under 653 over 2 hours,
  queued lookups under 707.

## Affected users and systems

- The GitLab pipelines panel: `PipelinesModel.js` (row status and text),
  `tests/model.cjs`, `README.md` (project row description), `manifest.json`
  (version). `Polling.js`, `gitlab.py` and `PipelinesPanel.qml` stay as they
  are: the panel already draws a row's icon and colour from its status
  (`PipelinesPanel.qml:752-758`).
- p620 and razer through the usual deploy chain. p510 is left alone.

## Constraints

- Must not add requests (keeps #35's savings).
- Must not change what counts as "running" or the pinned/running sort order.
- No new dependency.
- UI checks run in the microVM, never on the host desktop.

## Decisions (were open questions)

1. **Latest = newest on any ref**, as GitLab's pipelines page lists them,
   because that is the data the panel already holds.
2. **Source: what is already known** (option a). Fetching the newest
   pipeline per background check would add about 155 requests per 30
   minutes (626, over the 500 target); one initial fetch per project adds
   136 (607). A GraphQL sweep could cost about 12-30 more but needs a new
   API path, cursor handling and complexity limits that cannot be verified
   here. Rows of projects never selected and never seen running stay `·`
   until they are. A fetching option can follow as its own issue.
3. **Order unchanged.** The issue asks only for the icon.
