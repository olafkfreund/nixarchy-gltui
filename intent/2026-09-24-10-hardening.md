# Intent: Harden edge cases, add package metadata and CI

## Problem

The 2026-09-24 review found no High issues, but it left a set of small gaps.
All were re-verified on `main` at `8afa28e`.

- **A server can stop polling for good.** The rate-limit cooldown
  (`Polling.js:162-165`) has no upper bound. A broken proxy sending
  `Retry-After: 99999999` stops all polling until the shell restarts.
- **Bad helper replies can throw in the panel.** `Polling.complete` uses
  `reply.data` (`:187` onward) without checking its shape. `data: null`, or a
  non-list for a list request, throws instead of showing an error.
- **Odd HTTP replies are misread.** `http_reply` (`gitlab.py:83`) keeps reading
  header blocks for as long as the text starts with `HTTP/`, so a body that
  starts that way replaces the real status. A 3xx reply (for example after a
  project rename) goes on to the JSON decode, and the user sees "invalid data"
  instead of a clear message.
- **`menu.py` crashes with a traceback** instead of its short error when
  `quickshell list` returns entries without a string `config_path`.
- **The token could be sent to another host.** `host` in `shell.json` is only
  checked for format. If the user exports `GITLAB_TOKEN`, glab may send it to
  whatever host is configured. Unverified; only someone who can already edit
  the user's config could set it.
- **Packaging and CI.** The flake package has no `meta` (license,
  description, platforms), and nothing runs `nix flake check` on pull
  requests, so the checks only run when someone remembers.
- **Untested paths:** the 90 s overall deadline in `gitlab.py`, a garbled
  helper reply reaching the panel, `openBrowser` refusing a wrong-host URL, and
  the invalid-host config error.

## Proposed outcome

- Polling always resumes within a bounded time after a rate limit.
- Malformed helper replies and unexpected HTTP replies show a clear panel
  error, never an exception or a misleading message.
- `menu.py` reports malformed shell data with its normal one-line error.
- The token can't be sent to a host glab isn't logged in to (if open
  question 1 is yes).
- The package carries its license and description, and every PR runs
  `nix flake check` automatically.
- Each fix above, plus the listed untested paths, has a test.

## Affected users and systems

- Code: `Polling.js`, `gitlab.py`, `menu.py`, `PipelinesPanel.qml`
  (`configure` only, if question 1 is yes).
- Build: `flake.nix`, a new `.github/workflows/` file.
- Tests: `tests/polling.cjs`, `tests/test_gitlab.py`, `tests/test_menu.py`,
  `tests/qml-smoke.py`.
- Users: no change on the normal path; only failure cases behave better.

## Constraints

- No change to normal behaviour, keys, config keys or plugin id.
- No new runtime dependencies. CI may use standard GitHub-hosted actions.
- Out of scope, as decided in #7: renaming data fields, folding
  `keybindings.sh`. Also out: wrapping `python3`/`glab` into the package (the
  README documents them as user-provided, per the #1 spec), a `devShell`, and
  a formatter.

## Open questions

1. **Host allow-list.** Restrict `host` to hosts glab is logged in to? That
   means reading glab's config (`~/.config/glab-cli/config.yml`) or running
   `glab auth status`. Default if unanswered: **no**. It's defence in depth
   against someone who can already edit your config, and it adds a
   dependency on glab's config format.
2. **CI.** Run `nix flake check` on GitHub Actions for every PR and push to
   `main`? Default if unanswered: **yes**, x86_64-linux only.
