# Intent: Open the panel filtered to one project

## Problem

The shell hands each plugin a payload when it opens it:
`omarchy-shell shell summon <id> '<json>'` reaches `open(payload)`
(`PipelinesPanel.qml:93`) as a JSON string, through the shell's
`summon()` / `deliverIfLoaded()`. The panel ignores it. Every open path
sends `"{}"`: `menu.py:121` and `toggle()` (`PipelinesPanel.qml:114`).

So a user in a terminal, inside a project's checkout, cannot open the panel
on that project. They open it, press `/`, and type the path by hand.

## Proposed outcome

- **The payload can set the filter.**
  `omarchy-shell shell summon olafkfreund.gitlab-pipelines '{"filter":"group/project"}'`
  opens the panel with the search box set to `group/project`.
  - The list shows what that search shows today. That includes projects
    whose path or description contains the text, and the auto-opened
    projects from #27.
  - Keyboard focus is on the list, not the search box, so `j` / `k`, `o`,
    `y` and `e` work at once. The first row is selected, even when the same
    filter was already set, and the help overlay (#29) is closed.
  - Projects are not expanded beyond what the search already does (#27).
    The filtered open behaves exactly like typing the text after `/`.
  - Esc clears the filter, as it does for a typed search.
- **A filtered open replaces any filter already set,** including when the
  panel is already open (`summon`). If several payloads arrive at once,
  they apply in order, so the last valid filter wins. `toggle` on an open
  panel closes it and drops its payload, as the shell does today
  (`shell.qml:1274-1276`).
- **A missing, empty or bad payload behaves as today:**
  - invalid JSON;
  - a JSON value that is not an object (`null`, an array, a number);
  - a `filter` that is not a string;
  - an empty or blank filter;
  - a filter longer than the cap (see below), which is rejected, not
    truncated.

  The panel opens with its current filter and selection, and nothing is
  logged as an error.
- **The filter text is cleaned before use:** trimmed, with control
  characters removed. It must be at most 200 characters, so a payload
  cannot inject newlines or an oversized string into the search box.
- **The payload may name a host.** `{"filter": …, "host": "gitlab.example.org"}`
  only applies the filter when the host matches the panel's configured
  host (case-insensitive). Otherwise the panel opens without changing its
  filter, and the footer notice (#29) says
  `Repository is on <host>; this panel shows <panel host>`.
  - Without the host, a GitHub checkout `team/project` could match a
    different `team/project` on the GitLab host and show the wrong
    pipelines.
  - A payload without `host` is still accepted, as a plain filter.
- **A terminal command opens the panel on the current repository.**
  `menu.py` gains `open [FILTER]`:
  - it summons the panel with `{"filter": FILTER}`;
  - with no `FILTER`, it uses the current directory's Git remote. It runs
    `git remote get-url origin` and sends both the host and the project
    path. Supported forms:

    | Form | Example |
    |---|---|
    | SCP-style SSH | `git@host:group/sub/project.git` |
    | SSH URL | `ssh://git@host:2222/group/sub/project.git` |
    | HTTP(S) URL | `https://host:8443/group/sub/project.git/` |

    - The port and any user are dropped.
    - A trailing `/` is removed first, then a trailing `.git`.
    - Nested groups are kept.
    - Anything else (a local path, `file://`, a URL with no path) is
      unsupported.
  - With no Git remote or an unsupported one, it opens the panel without
    changing the current filter and prints why on stderr, exiting 0.

  The README shows the command and an example shell alias.
- **Tests** cover the payload parsing, the cleaning, the remote-URL
  parsing and the `menu.py open` command line. A microVM smoke step opens
  the panel with a payload.

## Affected users and systems

- Files: `PipelinesPanel.qml` (`open()`), `PipelinesModel.js` (a pure
  payload parser, so Node can test it), `menu.py` (`open`), `README.md`,
  `keybindings.sh` if it lists commands, and the tests: `tests/model.cjs`,
  `tests/test_menu.py` and `tests/qml-smoke.py`.
- No GitLab request changes. A filter only narrows what is already loaded,
  and discovery continues as today.
- It ships through the usual chain to p620 and razer; p510 stays on 1.0.0.

## Constraints

- `open("{}")`, the path every existing caller uses, must behave exactly
  as today.
- The payload is untrusted input from any local caller of `omarchy-shell`:
  parse it defensively, never `eval`, and never pass it to a shell.
  `menu.py` passes the JSON as one `argv` element.
- `menu.py open` builds the payload with `json.dumps`, never by string
  concatenation.
- No change to `Polling.js`, or to how search, auto-open (#27) and
  selection work once the filter is set.
- Smoke tests run in the microVM only, never on the host desktop.

## Open questions

1. **Which remote?** I recommend `origin` only, which is what most
   checkouts have. A fork with `upstream` would then show the fork's
   pipelines. A `--remote NAME` option can come later if needed.
2. **Length cap:** I recommend 200 characters. GitLab caps a single path
   segment at 255, so a deeply nested path could in theory be longer. A
   longer filter is rejected, so the worst case is the panel opening
   unfiltered.
3. **Expanding the project:** I recommend not expanding it for now. A
   filtered open then behaves exactly like a typed search, and the user
   presses Enter to expand. Expanding automatically would add to the
   user's own expanded set, which survives clearing the search
   (`README.md:181`); that can be its own issue.

## Review notes

Codex reviewed the draft read-only; agy is out of use (#2748). It confirmed
the problem, the line references, and that the shell's queued delivery
works when the panel loads late (`shell.qml:1282-1287,1305-1320`). Its
findings, which I checked in the code and folded in above:
- "unfiltered" contradicted "behaves as today": the fallbacks now all say
  the filter is left unchanged;
- a remote on another host could match a same-named GitLab project, since
  matching uses only the path (`PipelinesModel.js:131-132`): the payload
  now carries the host;
- auto-expanding conflicted with keeping #27's search behaviour: now not
  done, and listed as a question;
- the supported remote URL forms are now named, including ports, `ssh://`
  and a trailing slash;
- several payloads at once, `null` or array payloads, re-sending the same
  filter, `toggle` while open, and help being open are now covered.
