# Intent: A bar widget with running and failed counts

## Problem

You only learn that a pipeline is running or has failed by opening the
panel. Issue #41 asks for a small widget in the Omarchy bar that shows how
many pipelines are running and failed, and opens the panel when clicked. It
must reuse the panel's data and add no polling of its own while the panel
is closed, "unless watching (#34) is approved". #34 was approved and
shipped: watched pipelines are polled every 30 s, also while the panel is
closed.

Today:

- **The plugin is a panel only.** `manifest.json` declares `"kinds":
  ["panel"]`, one entry point (`PipelinesPanel.qml`) and `keepLoaded: true`.
  The keep-loaded panel is mounted at shell start (`shell.qml` lines
  1436-1439) but fetches nothing until it is first opened.
- **The shell supports bar widgets.** The shell reference
  (`docs/omarchy-shell.md`, "Plugin manifest") has a `bar-widget` kind with
  a `barWidget` entry point and manifest block. A widget is placed by an
  entry in `bar.layout.<section>` of `~/.config/omarchy/shell.json`. Each
  bar surface (screen) gets its own widget instance, rebuilt when the bar
  turns between horizontal and vertical ("Custom bar modules").
- **Adding `bar-widget` to this plugin changes how it is enabled.** For a
  plugin with that kind, `omarchy plugin enable` puts an entry in the bar
  layout instead of `plugins[]` (`PluginRegistry.qml` lines 556-575), and
  `listPlugins` reports it enabled only while it is on the bar
  (`shell.qml` lines 1965-1973). The panel reads `host`, `actions`,
  `projects` and `pinned` only from the `plugins[]` entry
  (`PipelinesPanel.qml`, `configure()`), so a user enabled that way would
  silently get `gitlab.com` and no settings, and existing users would see
  the panel listed as disabled. Adding `bar-widget` does keep
  `summon`/`toggle` on the panel path (`isBarWidgetPanelPlugin`,
  `shell.qml` lines 1190-1202).
- **Entry points cannot see each other.** A third-party plugin's `shell`
  facade (`PluginShellApi.qml`) can toggle its own id and look up its own
  `service` entry point (`shell.qml` `pluginServiceFor`, lines 422-425),
  but not another entry point's instance. A kept service survives a plugin
  hot-reload while the panel is rebuilt (`shell.qml` lines 1076-1095;
  reference line 50), and under a replacement bar a widget gets no service
  at all (reference line 54).
- **The panel can already be toggled from outside**:
  `omarchy-shell shell toggle olafkfreund.gitlab-pipelines '{}'` (README
  "Keyboard shortcuts"; `menu.py toggle`).
- **The data goes stale while the panel is closed.** `Polling.close`
  clears every task, and only watches are re-seeded while closed
  (`Polling.js` `close`, `next`, `seedWatches`). Project counts stay as
  they were at close, except where a watch reply updates its project.
- **A finished watch can stay counted as running.** When a watched
  pipeline ends while closed, `complete()` keeps `r.active` at
  `Math.max(r.active, running)` for projects whose count came from
  GitLab's total (`Polling.js` lines 459-461), so the project still says
  one running.
- **"Failed" is not one number today.** A project row's icon and `last
  <status>` show the latest *finished* pipeline the panel has seen for it
  (README "Projects"; `Model.latest`, `PipelinesModel.js` lines 66-72), on
  any branch; a newer running pipeline does not replace it, and a newer
  success hides an older failure. Activity checks fetch running pipelines
  only, so most projects have a latest finished pipeline only after being
  selected or seen running.
- **The panel's `updated` time moves on any reply**, including a single
  watch or job lookup, so it does not say how old the project counts are.
- **nixarchy installs the plugin** (`modules/home.nix`, the `gitlab`
  entry) and does not place third-party bar widgets.

The sister plugin has the same request (nixarchy-ghtui #62), not yet
designed.

## Proposed outcome

When this is done:

- **A bar widget** can be added to the Omarchy bar like any widget. It
  shows a small GitLab mark with two numbers when they are not zero: running
  pipelines and failed projects. It uses the bar's font, foreground and
  urgent colours, and reads correctly on horizontal and vertical bars.
- **Clicking it toggles the panel**, as the menu and keybinding do.
- **Every screen shows the same counts**, and adding widgets on more
  screens adds no requests.
- **The counts mean what the panel shows.** Running is the sum of the
  project rows' running counts. Failed is the number of projects whose
  latest finished pipeline the panel has seen failed. The tooltip and the
  accessible name say "N running pipelines, N failed projects", so the two
  units are not confused.
- **Watches keep it current while closed.** A watched pipeline that ends
  stops counting as running at once, panel open or not (fixing the stale
  `r.active` above), and counts as failed if it is now its project's latest
  finished pipeline and failed.
- **Freshness is honest.** The tooltip says when project counts were last
  refreshed (the last project activity read, not any reply), and that
  watched pipelines are live. Before the panel has loaded anything the
  widget shows the mark only, dimmed, with "Open GitLab Pipelines to load".
- **Stops show.** A sign-in, setup, configuration or rate-limit stop shows
  as a distinct state, not as zero, with the reason in the tooltip. A rate
  limit clears on its own when its time passes, even while the panel is
  closed. The merge-request view's errors do not affect the widget.
- **Resets are clean.** After a host change, a plugin reload or a shell
  restart the widget shows the no-data state until the panel loads again;
  it never shows another host's or an old instance's counts.
- **Existing installs are unaffected.** Enabling, disabling and listing the
  panel plugin behave as today, and its settings stay in its `plugins[]`
  entry.
- **No new polling by default** while the panel is closed (open
  question 3).
- **Docs**: the README explains how to add the widget, what the numbers
  mean, how fresh they are, and its limits.

## Affected users and systems

- **Everyone with the plugin**: nothing changes until the widget is placed,
  except the stale-running fix for watches.
- **Files** (the spec fixes the exact set): `PipelinesPanel.qml` (publishing
  the counts), `Polling.js` (the watch running-count fix), `PipelinesModel.js`
  (the count logic), new widget files (open question 1), `README.md`,
  `manifest.json` (1.16.0), tests (unit, polling, model, and the QML smoke
  test in the headless VM).
- **nixarchy**: if the widget is a second plugin (open question 1), nixarchy
  needs a second plugin entry to install it; that is a nixarchy change
  after this release.
- **Hosts**: p620 and razer on the 1.16.0 deploy. p510 is not touched.

## Constraints

- **No daemon, no token storage**; `glab` signs every request.
- **One scheduler, one budget.** The widget runs no polling loop and no
  helper process of its own.
- **No polling while closed by default**, except watches (issue text).
- **Theme-native**; a click toggles, nothing else.
- **GitLab text is untrusted (#15)**: anything from GitLab in the tooltip is
  plain text.
- **Documented shell API only.** No walking the host object tree.
- **No new runtime dependency.**

## Open questions

Recommendations follow the owner's earlier "use recommendations that make
sense".

1. **How is the widget packaged, and how does it get the counts?**
   (a) A second, widget-only plugin (`olafkfreund.gitlab-pipelines-bar`)
   shipped in this repo. The panel writes a small status file under the
   plugin's state directory (`$XDG_STATE_HOME/omarchy-gitlab-pipelines/`,
   where `pinned.json` already lives); the widget watches it and toggles
   the panel with `omarchy-shell shell toggle`. (b) Add `bar-widget` and a
   small `service` to this plugin; the panel publishes counts to the
   service and the widget reads it through `shell.serviceFor`.
   *Recommendation: (a). It leaves the panel plugin's enable, list and
   settings behaviour exactly as today, works under a replacement bar, and
   has no kept service to go stale across a reload. Its cost is a second
   plugin directory to install (README steps, and a nixarchy entry later).
   (b) changes `omarchy plugin enable` and Setup → Plugins for every user
   and would have to read settings from the bar entry too.*
2. **What counts as failed?** *Recommendation: projects whose latest
   finished pipeline the panel has seen failed (the project rows' icon),
   excluding archived, CI-disabled and unavailable projects. Not a count of
   failed pipelines, which would grow with history.*
3. **Should the widget cause background polling?** (a) Never; show the
   last known counts with their age. (b) While the widget is placed, a slow
   check of pinned projects with the panel closed.
   *Recommendation: (a), as the issue asks. Watches cover "keep an eye on
   this" today; (b) can be its own issue if stale counts prove useless.*
4. **Clicks.** *Recommendation: left click toggles the panel; no other
   buttons.*
5. **Does nixarchy place the widget?** *Recommendation: no; the user adds
   it with `omarchy bar put` or the bar settings.*
6. **Sister plugin.** *Recommendation: design it so nixarchy-ghtui #62 can
   copy it; no ghtui change here.*
