# Intent: A bar widget with running and failed counts

## Problem

You only learn that a pipeline is running or has failed by opening the
panel. Issue #41 asks for a small widget in the Omarchy bar that shows how
many pipelines are running and failed, and opens the panel when clicked. It
must reuse the panel's data and add no polling of its own while the panel
is closed, "unless watching (#34) is approved". #34 was approved and shipped
in v1.11.0: watched pipelines are polled every 30 s, also while the panel
is closed.

Today:

- **The plugin is a panel only.** `manifest.json` declares `"kinds":
  ["panel"]` and one entry point, `PipelinesPanel.qml`, with `keepLoaded:
  true`.
- **The shell supports bar widgets.** The Omarchy shell reference
  (`docs/omarchy-shell.md`, "Plugin manifest") lists a `bar-widget` kind
  with a `barWidget` entry point and a `barWidget` manifest block
  (`displayName`, `category`, `defaultSection`, `defaults`, `schema`). A
  manifest may declare several kinds; `omarchy.menu` is `menu` plus
  `bar-widget`. A widget is placed by an entry in `bar.layout.<section>` of
  `~/.config/omarchy/shell.json`.
- **Panel and widget are separate instances.** Each entry point is its own
  QML item. A third-party plugin gets a capability-scoped `shell` facade
  (`shell/services/PluginShellApi.qml`): it can `toggle`/`summon` and
  `isPluginOpen` its own id, and `serviceFor` its own id, which returns the
  instance of the plugin's `service` entry point if it has one
  (`shell.qml`, `pluginServiceFor`, lines 422-425). There is no lookup of
  another entry point's instance, so a widget cannot read the panel's
  state directly.
- **Adding `bar-widget` keeps the panel path.** `isBarWidgetPanelPlugin`
  (`shell.qml` lines 1190-1202) leaves plugins that are also `panel` to the
  panel loader, so `summon`/`toggle` of the panel are unchanged.
- **Service-backed widgets are fully supported only under the built-in
  bar.** The reference says a replacement bar hosts third-party widgets
  without their service.
- **The panel's data goes stale while closed.** `Polling.close` drops all
  tasks except watches (`Polling.js`, `close` and `next`). Project counts
  (`repo.active`, latest status) stay at whatever they were when the panel
  closed. Watches keep their pipeline's status current and end when it
  finishes, with a desktop notification.
- **Nothing is known before the first open.** The keep-loaded panel is
  mounted at shell start, but nothing is fetched until it is opened.
- **"Failed" is not one number today.** A project row shows its latest
  known pipeline as `last <status>`; there is no count of failed
  pipelines, and the panel only knows the latest pipelines of projects it
  has checked.
- **nixarchy installs the plugin** (`modules/home.nix`, the `gitlab`
  entry, id `olafkfreund.gitlab-pipelines`) and enables it as a panel. It
  does not place bar widgets for third-party plugins today.

The sister plugin has the same request (nixarchy-ghtui #62), not yet
designed.

## Proposed outcome

When this is done:

- **A bar widget** can be added to the Omarchy bar (by `omarchy bar put`
  or the bar settings, like any widget). It shows a small GitLab icon with
  the number of running pipelines and the number of failed ones, each only
  when non-zero, using the theme's bar font, foreground and urgent colours.
- **Clicking it toggles the panel.** The panel opens as it does from the
  menu or keybinding.
- **It shows the panel's data, honestly dated.** The counts come from the
  same polling state the panel uses. While the panel is closed and
  nothing is watched, the counts are the last ones seen, and the tooltip
  says when they were last updated; the widget does not pretend they are
  live. Before the panel has fetched anything it shows only the icon and
  a tooltip saying to open the panel (open question 4).
- **No new requests by default.** Placing the widget adds no polling while
  the panel is closed, beyond what open question 3 decides.
- **Watched pipelines count.** A watched pipeline that is running counts
  as running, and one that ends failed counts as failed, as soon as the
  watch sees it, panel open or not.
- **Errors show.** A sign-in, setup or rate-limit stop shows as a distinct
  state on the widget (not as zero), with the panel's message in the
  tooltip.
- **Theme-native and accessible.** No new colours; the widget has an
  accessible name with the counts.
- **Docs**: the README explains how to add the widget, what the numbers
  mean, how fresh they are, and that a replacement bar may not show it.

## Affected users and systems

- **Everyone with the plugin**: the manifest gains a kind; nothing appears
  in the bar until the widget is placed.
- **Files**: `manifest.json` (kinds, entry point, `barWidget` block, 1.16.0),
  a new widget QML file, a shared state path between panel and widget
  (open question 1: a small `service` entry point, or the panel itself
  becoming reachable), `PipelinesPanel.qml` and/or `Polling.js` for the
  counts, `PipelinesModel.js` for the count logic, `README.md`,
  `keybindings.sh` (if a key is added), tests (unit, polling, and the QML
  smoke test in the headless VM).
- **nixarchy**: may want a `programs.nixarchy` option to place the widget;
  out of scope here unless the owner wants it (open question 6).
- **Hosts**: p620 and razer on the 1.16.0 deploy. p510 is not touched.

## Constraints

- **No daemon, no token storage**; `glab` signs every request.
- **One scheduler, one budget.** The widget does not run its own polling
  loop or helper process; any background reads go through `Polling.js`
  and its limits.
- **No polling while closed by default**, except watches (issue text).
- **Theme-native, no buttons beyond the widget itself**; click to toggle.
- **GitLab text is untrusted (#15)**: anything from GitLab shown in the
  tooltip is plain text.
- **Works with the shell's facade.** No reaching into host objects outside
  the documented `shell` API, even though QML would allow it.
- **No new runtime dependency.**

## Open questions

Recommendations follow the owner's earlier "use recommendations that make
sense".

1. **How does the widget get the panel's data?** (a) Add a `service` entry
   point that owns the polling state and helper process; the panel and the
   widget both read it through `shell.serviceFor`. (b) Keep polling in the
   panel and add a tiny `service` that only holds published counts, which
   the panel writes after each update. (c) The widget reads the panel's
   instance some other way (walking the host object tree).
   *Recommendation: (b). It is the smallest change that uses the
   documented facade: the panel stays as it is and publishes `{running,
   failed, error, updatedAt}` after each `adopt()`; the widget only reads.
   (a) is the cleaner long-term shape but moves the whole scheduler; (c)
   relies on host internals the docs warn against.*
2. **What does "failed" count?** (a) Projects whose latest known pipeline
   failed. (b) Failed pipelines among those the panel holds. (c) Only
   watched pipelines that ended failed since the last open.
   *Recommendation: (a), "projects whose latest pipeline failed", which
   matches the project rows' `last failed` and does not grow with history.
   Running is the sum of the projects' running counts, as in the header.*
3. **Should the widget cause background polling?** (a) Never; show the last
   known counts with their age. (b) While the widget is placed, keep a slow
   activity check (for example the pinned projects every 5 minutes) with
   the panel closed.
   *Recommendation: (a) now, as the issue asks. Pins and watches already
   cover the "keep an eye on this" case; (b) can be its own issue if the
   stale counts prove useless.*
4. **What does it show before any data?** *Recommendation: the icon only,
   dimmed, with the tooltip "Open GitLab Pipelines to load". No number.*
5. **Clicks.** *Recommendation: left click toggles the panel. No
   right-click or middle-click actions.*
6. **Does nixarchy place the widget?** *Recommendation: no; the user places
   it with `omarchy bar put olafkfreund.gitlab-pipelines` or the bar
   settings. A nixarchy option can follow in nixarchy itself.*
7. **Sister plugin.** *Recommendation: design it so nixarchy-ghtui #62 can
   copy it, but do not change ghtui in this task.*
