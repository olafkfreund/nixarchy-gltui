# Intent: Help, copy, jump, close and next-failure keys

## Problem

The panel's keys cover moving, expanding, searching, refreshing, opening
GitLab and zoom (`PipelinesPanel.qml:331-351`). Some common actions are
missing or awkward:

- **No help inside the panel.** The only full key list is a separate menu
  (`keybindings.sh`, Super + Ctrl + Alt + P) that closes the panel first
  (`keybindings.sh:33`). The footer (`PipelinesPanel.qml:518`) lists only
  some keys and elides at narrow widths and high zoom.
- **No copy.** To share a pipeline or job link, or a commit, the user opens
  GitLab with `o` and copies from the browser. Rows already carry the URL
  (`url`, `PipelinesModel.js:172-212`). The commit SHA is cut to 8
  characters in the helper (`display_title`, `gitlab.py:151`), so the full
  SHA never reaches the panel.
- **No quick top and bottom.** Home and End work
  (`PipelinesPanel.qml:341-342`), but there is no vim-style `g` / `G` to
  match `j` / `k` / `h` / `l`.
- **Closing needs Esc, sometimes twice.** Esc first clears an active filter
  (`:334-336`), then closes. There is no single key that always closes.
- **Failures are hard to find.** In a long list the user scrolls and reads
  colours to find a failed pipeline or job.
- **The footer does not change while typing a search.** It still lists
  `r`, `o` and the other navigation keys (`:518`), which type letters into
  the search box at that point (`:373-389`).

## Proposed outcome

New keys, outside search typing:

| Key | Action |
|---|---|
| `?` | Show or hide a help overlay inside the panel, listing every key |
| `y` | Copy the selected row's GitLab URL |
| `Y` | Copy the full commit SHA of the selected pipeline, or of a stage or job's pipeline |
| `g` / `G` | Jump to the first / last row |
| `q` | Close the panel, even with a filter active |
| `e` | Select the next failed row after the cursor, wrapping to the top |

- **Copy** puts the text on the Wayland clipboard with `wl-copy`, the way
  the Omarchy shell's own panels do. The footer then briefly confirms what
  was copied, for example `Copied URL` or `Copied 1a2b3c4d`, only after
  `wl-copy` exits successfully. If it is missing, fails to start or exits
  non-zero, the footer says `Copy failed`. A row with nothing to copy (a
  project row for `Y`, a message row) says so instead, and the clipboard is
  left alone. A confirmation takes precedence over the normal hint and the
  cooldown text for about two seconds.
- **Next failure** looks only at rows already in the list (expanded and
  filtered, including rows scrolled out of view), so it never expands
  anything or fetches. "Failed" means a pipeline, stage or job row whose
  status is exactly `failed`. "Allowed to fail", canceled rows and project
  or loading errors (`error`, `unavailable`, which `Model.group` also
  classes as failed) do not count.
  When there is none, the footer says so and the cursor stays.
- **Help** is an overlay inside the card: the same key list as
  `keybindings.sh`, readable at every zoom, scrollable if needed. `?`, Esc
  or `q` closes it. The zoom keys still work while it is open; other keys
  do nothing.
- **Closing resets** the help overlay and any copy confirmation, so the
  panel reopens in its normal state.
- **While typing a search,** the footer shows the search keys instead:
  `↑↓ select  Enter open  Tab navigate  Esc clear`.
- The README keyboard table, `keybindings.sh` and the footer list the new
  keys, and the README's requirements name `wl-copy` next to `xdg-open`.

## Affected users and systems

- Files: `PipelinesPanel.qml` (keys, footer, help overlay, copy),
  `gitlab.py` (pass the full `sha` with each pipeline),
  `PipelinesModel.js` (carry the SHA on rows; a pure "next failure" helper),
  `keybindings.sh`, `README.md`, and the tests: `tests/test_gitlab.py`,
  `tests/model.cjs` and `tests/qml-smoke.py`.
- `wl-copy` (wl-clipboard) must be on the shell's `PATH`. It is part of
  Omarchy's base set, which its own panels rely on.
- It ships through the usual chain to p620 and razer; p510 stays on 1.0.0.

## Constraints

- No clash with the zoom keys (Ctrl + `=` / `+` / `-` / `0`, #22): zoom keys
  are checked first, as today (`:332`), and the new keys ignore presses
  with Ctrl, Alt or Super held.
- `y` / `Y` and `g` / `G` are told apart by Shift, as `r` / `R` already is
  (`:346`). `?` is matched by the character typed, not a key code, so it
  works on layouts where it needs Shift or sits elsewhere.
- Search typing is unchanged: every printable key, including `?`, `q`,
  `g` and `y`, still types into the search box (`:373-389`).
- Copy only uses text the panel already holds; no new GitLab request. The
  full SHA comes from the pipeline list reply the helper already fetches.
- Server strings stay plain text (`Text.PlainText`). Copy passes the text
  to `wl-copy` as its own argument, never through a shell.
- Selection, scroll and zoom-settle behave as today; no binding loop.
- Smoke tests run in the microVM only, never on the host desktop.

## Open questions

1. **Where help lives:** I recommend an overlay inside the card (above).
   The alternative, opening the existing keybindings menu, hides the panel
   (`keybindings.sh:33`) and puts a second window in front of it.
2. **What `e` finds:** I recommend shown rows only, failed pipelines,
   stages and jobs, wrapping. The alternative,
   searching inside collapsed pipelines, needs job lists the panel may not
   have fetched, so it would fetch or expand behind the user's back.
3. **`Y` on a project row:** I recommend "No commit for this row" in the
   footer, not the latest pipeline's SHA, so that the copied SHA always
   matches what the user selected.
4. **Copy confirmation:** I recommend the footer for about two seconds.
   A desktop notification would be noisier for a frequent action.

  (`close()` keeps it, `:93-97`), so it is removed;
- the footer reference is `:518`;
- next failure uses exact `failed`, since `group()` also classes `error`
  and `unavailable` as failed (`PipelinesModel.js:23`);
- confirmation precedence and a reset on close are now stated.

I checked that `wl-copy` is on `PATH` here and that the Omarchy shell's
network panel copies the same way (`Panel.qml:508`). Copying from the
layer surface itself is verified in the microVM smoke test.
