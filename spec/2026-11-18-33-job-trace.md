# Spec: Open a job's log with t

## Design

Four parts: the job id on job rows, a `trace` verb in `menu.py`, the `t`
key in the panel, and the docs.

### 1. Job id on job rows (`PipelinesModel.js`)

Job rows (`PipelinesModel.js:254`) gain `job: String(job.id)`. The id is
GitLab's: `gitlab.py`'s `job()` keeps `row["id"]` only when it is an `int`
of 1 or more (`gitlab.py:193`). Nothing parses the row key or looks a job
up by name. `job` is not displayed, so it does not join `shownFields`.

### 2. `menu.py trace HOST PROJECT JOB`

- **Placement:** `main()` handles `trace` first, before the usage check
  and before the Quickshell session lookup (`menu.py:162`). Tracing needs
  no shell session.
- **Arguments:** exactly three after `trace`, else the usage error. The
  usage text becomes
  `menu.py [keys|toggle|register|open [FILTER]|trace HOST PROJECT JOB]`.
- **Validation,** each failure a `ValueError` (stderr
  `GitLab Pipelines: <message>`, exit 1, nothing started):
  - `HOST` with `gitlab.py`'s `host_name`;
  - `PROJECT` with `gitlab.py`'s `project_path`;
  - `JOB` must match `[1-9][0-9]{0,18}`, else `Invalid job`.

  `gitlab.py` is loaded from `menu.py`'s own directory with
  `importlib.util.spec_from_file_location`, so the rules are the same code,
  not a copy.
- **Command:**

  ```python
  TRACE = 'glab ci trace "$1" -R "$2"; printf "\\nPress Enter to close. "; read -r _'
  ["omarchy-launch-tui", "--app-id=org.omarchy.gitlab-trace",
   "sh", "-c", TRACE, "sh", JOB, f"https://{HOST}/{PROJECT}"]
  ```

  - The script is a constant. `JOB` and the URL arrive as `$1` and `$2`,
    and are only ever expanded in double quotes, so they are never parsed
    as shell source.
  - `omarchy-launch-tui` runs `setsid uwsm-app -- xdg-terminal-exec
    --app-id=… -e "$1" "${@:2}"`, which passes the arguments through
    unchanged.
  - The port in `HOST` is kept. Checked with glab 1.130.0 and a local
    listener: `glab ci trace 1 -R https://localhost:18443/g/p` connected to
    port 18443.
- **Launch and hand-off:** `proc = subprocess.Popen(command,
  start_new_session=True, stdin=DEVNULL, stdout=DEVNULL, stderr=DEVNULL)`,
  then `proc.wait(timeout=2)`:
  - **still running after 2 s:** exit 0. With a terminal that runs in the
    launcher's scope, `uwsm app` keeps the launcher alive while the
    terminal is open, so a live launcher means the terminal started;
  - **exited 0 within 2 s:** exit 0 (a terminal that hands the window to
    an existing instance and returns);
  - **exited non-zero within 2 s:** stderr
    `GitLab Pipelines: terminal launcher failed (exit N)`, exit 1. This
    covers a missing `uwsm-app` or `xdg-terminal-exec`, or no usable
    terminal;
  - a missing `omarchy-launch-tui` raises `OSError` from `Popen`, which
    `main()` already turns into stderr and exit 1.

  Starting the launcher in its own session, rather than `execvp`, lets
  `menu.py` return while the terminal stays open. The limit, stated in the
  README: a terminal that fails more than 2 s after starting is reported
  in its own window, or not at all.

### 3. The `t` key (`PipelinesPanel.qml`)

- **New properties:** `traceCommand: ["python3", localPath("menu.py"),
  "trace"]`, a test hook like `copyCommand`, `traceStarted: false` and
  `traceSerial: 0`.
- **`trace()`:**
  - if `current` is not a job row, or has no `job`: notice
    `Select a job to open its log`, and return;
  - if `traceProc.running`, return;
  - `traceStarted = false`;
    `traceProc.serial = traceSerial`;
    `traceProc.command = traceCommand.concat([host, current.repo, current.job])`;
    `traceProc.running = true`.
- **`close()`** also increments `traceSerial`, as it does `copySerial`
  (`PipelinesPanel.qml:145`), so a trace still pending when the panel
  closes neither closes a later opening nor shows a stale notice.
- **`traceProc`:** a `Process` with `property int serial`, using the same
  serial guard and failed-start rule as `copyProc`
  (`PipelinesPanel.qml:455-463`). Every callback first checks
  `serial === root.traceSerial`:
  - `onStarted`: `traceStarted = true`;
  - `onExited(code)`: code 0 → `close()`; otherwise notice
    `Could not open a terminal`;
  - `onRunningChanged`: not running and not started → notice
    `Could not open a terminal`.
- **Key:** in the `plain` chain, unshifted:
  `else if (plain && event.key === Qt.Key_T && !shift) root.trace()`.
  - The search box keeps its own key handling, so `t` types there.
  - The help-open branch comes first in the handler, so `t` does nothing
    while help is open.
- **Hint:** `listHint` gains `t log` after `p pin`.

### 4. Docs and version

- **`README.md`:**
  - Requirements (`:11`): add "a terminal that `xdg-terminal-exec` can
    start with a command (Omarchy's terminals can), for the log key";
  - the Keyboard table: `| t | Open the selected job's log in a terminal |`
    after `p`;
  - "Open GitLab for logs." (`:225`) becomes "Press **t** on a job to
    follow its log in a terminal (`glab ci trace`), or **o** to open it on
    GitLab." It adds: if no terminal can be started, the panel stays open
    and says `Could not open a terminal`; errors after the terminal opens
    show in that window.
- **`keybindings.sh`:** after the `p` line,
  `t → Open the selected job's log in a terminal`.
- **`manifest.json`:** `1.8.0`.

## Alternatives rejected

- **Building the terminal command in QML:** it would put the validation
  in a second language with no unit tests, and duplicate `gitlab.py`'s
  rules.
- **`execvp` the launcher from `menu.py`:** the launcher only exits when
  the terminal closes, so the panel could not tell a failed launch from an
  open terminal, and would stay open on top of it.
- **`Quickshell.execDetached`:** reports nothing, so a failed launch would
  close the panel silently.
- **A `GITLAB_HOST` environment variable instead of a URL:** it also works,
  but the URL keeps everything in the arguments and needs no environment
  change.
- **Pipeline rows:** `glab ci trace` without a job asks interactively
  (intent, question 4).

## Risks

- **The terminal:** one that ignores the command after `-e` shows a plain
  shell. The README names the requirement. Omarchy's terminals (Alacritty,
  foot, Ghostty, Kitty) run it.
- **Authentication:** `glab` in the terminal uses the user's login or
  environment token, as the panel's `glab` does, but from the terminal's
  environment rather than the shell's. A token set only for the shell
  (#31) may differ. `glab`'s error shows in the window, which stays open.
- **Hosts:** p620 and razer through the usual chain. p510 stays on its
  current version.

## Verification

- **`tests/model.cjs`:** job rows carry `job` equal to GitLab's id; two
  jobs with the same name keep their own ids.
- **`tests/test_menu.py`:**
  - `trace gitlab.example.org:8443 g/s/p 42` calls `Popen` once with
    exactly the command above, `start_new_session=True` and the three
    `DEVNULL` streams; returns 0; does not call `quickshell list` or
    `execvp`;
  - rejected, with exit 1, nothing started and the stderr message: a bad
    host (`-x`, `a b`), a bad project (`p`, `g/../p`, `g/p;x`), a bad job
    (`0`, `-1`, `1a`, `12345678901234567890`, `$(x)`), and two or four
    arguments;
  - `Popen` raising `FileNotFoundError` gives exit 1 and a stderr line;
  - with a real `Popen` of small scripts in place of the launcher: one
    that sleeps 5 s gives exit 0 after about 2 s; one that exits 0 gives
    exit 0; one that exits 3 gives exit 1 and
    `terminal launcher failed (exit 3)`;
  - the shell script, run for real with `sh -c TRACE sh '$(touch X)' 'u;v'`
    and a fake `glab` on `PATH` that prints its arguments, prints them
    unchanged and creates no `X`. `read` gets an empty stdin and returns
    (the script's own status is then non-zero, from `read`; the test
    checks the output, not the status). A fake `glab` that exits 1 still
    leaves the prompt printed.
- **`tests/qml-smoke.py`, in the microVM only:**
  - `t` on a project row and on a pipeline row: notice
    `Select a job to open its log`, panel open;
  - `t` on a job row with `traceCommand` set to a script that writes its
    arguments to a file and exits 0: the panel closes, and the file holds
    the host, project and job id;
  - a script exiting 1, and a missing binary: notice
    `Could not open a terminal`, panel open;
  - a script that sleeps 1 s and exits 0, with the panel closed and
    reopened before it exits: the reopened panel stays open and shows no
    notice (the serial guard);
  - `t` on a stage row and with the list empty: the job notice;
  - `t` typed in the search box goes into the filter text;
  - Ctrl, Alt, Meta and Shift + T do nothing; `t` with help open does
    nothing;
  - the footer hint and the help text include `t`.
- **Acceptance in the microVM:** a fake `glab` prints `FAKE LOG`, and
  writes to a marker file one line per argument, then `tty-in` / `tty-out`
  when its stdin / stdout is a terminal (`[ -t 0 ]`, `[ -t 1 ]`). It goes
  in a directory put first on `PATH` for the `menu.py` call.
  - Run `python3 menu.py trace gitlab.example.org g/p 42`; its exit code is
    0.
  - The marker file must exist, which proves the fake ran and not a real
    `glab`. If `PATH` does not survive `uwsm app`, the fake goes in
    `~/.local/bin` of the VM user instead, and the check is repeated.
  - The marker holds exactly the lines `ci`, `trace`, `42`, `-R`,
    `https://gitlab.example.org/g/p`, `tty-in`, `tty-out`.
  - A screenshot shows the terminal with `FAKE LOG` and
    `Press Enter to close.`. After Enter is typed, the window closes.
- All existing tests pass, and the flake's `plugin` check builds.

## Review notes

Codex reviewed the draft read-only; agy is out of use (#2748). It
confirmed the shell script's safety (constant source, `$0` placeholder,
quoted positionals, fixed `printf`), that `DEVNULL` and a new session do
not stop the terminal giving its shell a TTY, that loading `gitlab.py`
has no side effects (signal handlers live in its `main()`), the key
placement and the line references. Its findings, which I checked and
folded in above:
- returning 0 right after `Popen` would close the panel even when the
  launcher fails a moment later: `menu.py` now waits up to 2 s and reports
  a non-zero exit, with the limit stated;
- a late trace result could close a reopened panel: a `traceSerial`
  guard, as for copy, with a test;
- the acceptance check now proves the fake ran, the argument boundaries
  and the TTY, and handles `PATH` not surviving `uwsm app`.
