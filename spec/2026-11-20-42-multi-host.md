# Spec: Show more than one GitLab host at once

## Design

One `Polling` state per host, a panel-level host list that routes every
row, request, reply and action to its own host's state, and host-qualified
row keys that are byte-for-byte today's keys when only one host is
configured.

### 1. Configuration (`PipelinesPanel.qml` `configure()`, `gitlab.py`)

The plugin entry gains an optional `hosts` list:

```json
{"id": "olafkfreund.gitlab-pipelines",
 "hosts": [
   {"host": "gitlab.com", "pinned": ["me/site"]},
   {"host": "gitlab.example.org", "actions": true, "projects": ["team/app"]}
 ]}
```

- `hosts` absent or `[]`: today's single-host form (`host`, `actions`,
  `projects`, `pinned` at the top level), unchanged.
- `hosts` a non-empty array: it replaces the four top-level keys, which
  are then ignored (the README says so). Each item must be an object with
  a `host` string matching today's host pattern
  (`^[A-Za-z0-9][A-Za-z0-9.-]*(:[0-9]{1,5})?$`); `actions`, `projects`
  and `pinned` are read per item exactly as today's top-level keys.
- Anything else (`hosts` not an array, an item that is not an object, a
  missing or invalid `host`) is a config error: the panel shows it as
  today's invalid-host error, polls nothing, and the bar shows stopped.
- Duplicates, compared case-insensitively on the whole `host` including a
  port, keep the first. At most 4 hosts are used, in list order; the rest
  are named once in a notice ("Ignored hosts: a, b; at most 4 are shown")
  and in the shell log.
- One parse function, `Model.hostConfig(entry)`, returns
  `{hosts: [{host, actions, projects, pinned}], ignored: [...], error}` and
  is used by `configure()`. `gitlab.py actions_enabled(host)` mirrors it
  in Python (same validation, dedup and cap; any error means `False` for
  every host), with a shared fixture in `tests/` so both agree.

### 2. Per-host polling state (`Polling.js`, `PipelinesPanel.qml`)

- The panel keeps `pollers`: an array in config order of
  `{host, epoch, state}`, where `state` is a `Polling.create()` object.
  Everything per host in `Polling.create()` (repos, details, tasks,
  `starts`, cooldown, auth stop, errors, watches, merge requests) is
  therefore separate by construction. `Polling.js` keeps its single-host
  API; it gains no knowledge of other hosts.
- **Scheduling.** `Polling.next` is split into `Polling.choose(s, now)`,
  which does everything `next` does up to picking the task and returns
  `{task, group}` or `null` without committing, and `Polling.commit(s, t,
  now)`, which does the rest (slot, starts, requests, flight). `next` stays
  as `choose` + `commit`, so `tests/polling.cjs` keeps passing. The
  panel's `pump()` (still one read at a time, `workerBusy`) asks every
  host's `choose`, takes the best group (`interactive` < `active` <
  `pinned` < `background`), breaks ties round-robin starting after the
  host served last, commits on that host and sends the request with that
  host's name. Paused, stopped and idle hosts return `null` from `choose`
  as today, so they are skipped. Each host keeps today's 60-pages and
  one-second limits on its own `starts`.
- **Replies.** `requestInfo` records the host and epoch. `receivePage`
  hands the reply to that host's state only if a poller with that host and
  epoch still exists; otherwise the reply is dropped and `workerBusy` is
  cleared as today.
- **Open, close, select, refresh.** `open`, `close`, `view` and `manual`
  apply to every host's state. `select`/`selectMr`/`jump` go to the host of
  the current row, and every other host is selected with `""` (so only one
  host has an interactive selection). `r` refreshes the current row's host
  (or every host when there is no row); `Shift + R` refreshes every host.
- **Adding and removing hosts.** `configure()` compares the new host list
  with `pollers` by lowercased `host`:
  - kept: settings (`projects`, `pinned`, `actions`) update in place, data
    stays;
  - removed: its watches end with a notice naming the host, an unsent
    action for it is dropped ("Host removed; nothing was sent"), its state
    is discarded, and its `starts` and `writeAt` are remembered in
    `hostBudget[host]` for a minute so re-adding it cannot exceed its
    budget;
  - added: a new state, seeded from `hostBudget` if present, opened if the
    panel is open, and its pins loaded.
  - The single-host case, where the one host is replaced by another, keeps
    today's exact behaviour (`Polling.resetHost`, `hostEpoch`, the
    "now uses X, not Y" notice).

### 3. Rows and keys (`PipelinesModel.js`)

- The panel passes `Model.rows` the concatenation of every host's repos,
  each tagged with `host` only when more than one host is configured, and
  merged `details`, `pinned` and `watched` maps whose keys get the same
  prefix.
- The prefix is `q = repo.host ? repo.host + "|" : ""`. `repoKey` becomes
  `"repo:" + q + path`, `runKey` `q + path + ":" + id`, and the
  `details`/`pinned`/`watched` lookups use `q + path`. All child keys
  derive from these. With one host `q` is `""`, so every key, row and test
  fixture is unchanged.
- Each row carries `host` (`""` with one host). The repo row shows a
  dimmed host label after the title, `repoMatches` also matches the host,
  and `accessibleName` appends "on <host>". Sorting stays global (pinned,
  then running first).
- `Model.mrRows` takes `[{host, mrs}]`: rows are each host's list in
  order, concatenated in host order, with keys `"mr:" + q + id!iid`, a
  host label, and one "more on GitLab" row per truncated host (key
  `"mr:more:" + host`, its own dashboard link). One host: unchanged.
- Links and copies use the row's own host (`Model.browsable(url,
  row.host || host)`), job traces pass `current.host`, and `jumpMr` looks
  up the project id in that host's repos only.

### 4. Pins, watches, actions

- **Pins.** QML keeps a per-host map `pinState[host] = {config, saved,
  loaded, loadFailed}` in place of the scalar `configPins`, `savedPins`,
  `pinsLoaded`, `pinsLoadFailed` and `pinsLoadHost`. Loads run one host
  at a time on the existing `pinsLoad` process; saves stay serialized on
  `pinsSave` (each save rereads and replaces the whole file). `p` toggles
  the pin on the current row's host. The 10-pin cap is per host. The
  store format (`pinned.json` `hosts`) is unchanged.
- **Watches.** Watches stay in each host's state. The 5-watch cap counts
  across all hosts: the panel refuses a sixth before calling
  `Polling.watch`, with today's message.
- **Actions.** `actionsOn` becomes per host (`actionsFor(host)`); the
  actions-off hint names the row's host. The confirmation carries
  `host` and that poller's epoch; `sendAction` checks that the host is
  still configured with actions on and the epoch unchanged ("Host changed;
  nothing was sent" otherwise), and uses that host's `cooldown`,
  `lastStarted` and `writeAt`. Actions keep today's exception: one at a
  time on `actionProc`, alongside a read. `Model.describe` appends
  "on <host>" when more than one host is configured.
- **Notices.** `drainEvents` drains each host's events and passes its host
  to `Model.watchMessage`, whose texts add "on <host>" in multi-host mode
  (the auth text becomes "Run glab auth login --hostname <host>.").

### 5. Open from a repository (`Model.openFilter`, `applyOpen`)

`Model.openFilter(payload, hosts)` matches the payload's host against the
configured hosts by hostname (case-insensitive, port ignored, as today)
and returns `{filter, host, notice}`; the first configured match wins. With
several hosts, `applyOpen` also sets `openHost`, which limits matching to
that host until the filter text is edited or cleared. The notice ("is on
X; this panel shows Y, Z") appears only when no host matches.

### 6. Errors, header, `status()`

- The error strip lists one line per failing host, prefixed with the host
  in multi-host mode (`maximumLineCount` grows to the host count + 1).
  With one host the text is today's. A host whose catalogue never loaded
  has no rows, only its line; a host that fails later keeps its rows.
- The header says "N projects on K hosts" in multi-host mode;
  `discoveryComplete` is true when every host is complete or stopped.
- `status()` keeps today's top-level fields, taken from the first host,
  except `requests` and `mrs`, which are summed, and adds `hosts`:
  `[{host, discoveryComplete, error, requests, cooldown, lastRequest,
  lastStarted, actionsOn, mrs}]`.

### 7. Bar status (`Model.barStatus`, `bar-widget/BarModel.js`)

The file stays `version: 1` with every current field, plus an optional
`hosts` array of `{host, state, running, failed, countsAt,
cooldownUntil, reason}`. Top-level values for several hosts:

- `running` and `failed`: sums over hosts in state `ok` or `rate` that
  have counts.
- `state`: `stopped` for a config error or when every host is stopped;
  else `ok` if any host is `ok`; else `rate` if any host is paused (with
  the earliest `cooldownUntil`); else `none`.
- `countsAt`: the oldest `countsAt` among the counted hosts; `host`: the
  first host plus " +N" (for example `gitlab.com +1`); `reason`: the
  first stopped host's reason, prefixed with its host.

An old widget therefore shows the totals and a sensible tooltip. The new
widget, when `hosts` has more than one entry, adds one tooltip line per
host ("gitlab.example.org: stopped — Authenticate…"). With one host the
file and the widget are unchanged.

### 8. Single-host compatibility

With one host (or `hosts` absent), every row key, text, notice, `status()`
field and status-file byte is today's. This is checked by the existing
unit and smoke tests passing unchanged, apart from new cases.

## Alternatives rejected

- **One merged `Polling` state with host-qualified repo names.** Fewer
  QML changes, but the budget, cooldown, auth stop and errors would stay
  shared, which the intent rules out.
- **One worker per host in parallel.** Removes the slow-host delay but
  needs one `Process` per host, parallel reply routing and a new
  in-flight rule; the intent keeps one read at a time.
- **Rows grouped under host headings.** Breaks the global running-first
  order and adds a row level.
- **A plain list of host names.** Makes `projects` and `pinned` ambiguous
  and actions all-or-nothing.
- **Bumping the status file to version 2.** Old widgets reject anything
  but version 1 and would show "no data".
- **Treating an invalid `hosts` item as skipped.** A typo would silently
  drop a host and could leave actions on elsewhere; an error is clearer.

## Risks

- **Single-host regressions** in a large change to `PipelinesPanel.qml`.
  Mitigated by keeping keys and texts identical with one host and running
  the whole existing smoke unchanged.
- **A slow or unreachable host** delays the others by up to one request
  timeout (25 s) per turn until its backoff grows; documented as a limit.
- **Same path and id on two hosts** is the main mixing risk; the smoke
  test uses exactly that fixture.
- **`gitlab.py` and QML disagreeing** on which host has actions: the
  shared fixture tests both parsers against the same cases.
- **Environment tokens**: `glab` may send `GITLAB_TOKEN` to several
  configured hosts; README warns.
- Hosts: p620 and razer after release; p510 untouched.

## Verification

- `node tests/polling.cjs`: `choose`/`commit` equal `next`; existing
  cases pass.
- `node tests/model.cjs`: `hostConfig` (absent, empty, valid, invalid
  item, duplicates, more than 4), host-qualified keys with one host equal
  today's, two hosts with the same path and MR id give distinct keys and
  labels, `mrRows` per-host "more" rows, `openFilter` matching, `describe`
  and `watchMessage` host texts, `barStatus` aggregation (mixed ok,
  rate, stopped, none, config error).
- `node tests/bar.cjs`: an old-format file and a multi-host file; the
  tooltip host lines.
- `python3 -m unittest discover -s tests`: `actions_enabled` against the
  shared fixture.
- `nix build .#bar .#checks.x86_64-linux.plugin`.
- VM smoke, `nix build ./ci#checks.x86_64-linux.qml-smoke -L --no-link
  --override-input gltui path:<worktree>`, never on the desktop: every
  existing stage unchanged, plus a two-host stage where the fake helper
  serves the same path and ids on `gitlab.example.org` and
  `gitlab.other.org`: rows, selection routing (requests carry the right
  host), pins per host, an action confirmed on one host is sent to it,
  one host failing auth while the other keeps updating, removing a host
  with a request in flight (late reply ignored), the open filter, and the
  status file totals.
