# Spec: A bar widget with running and failed counts

The approved intent's recommendations are taken as decisions:
1. a second, widget-only plugin, fed by a status file the panel writes;
2. "failed" counts projects whose latest finished pipeline the panel has
   seen failed;
3. no background polling while the panel is closed;
4. a left click toggles the panel;
5. nixarchy does not place the widget;
6. it is designed so nixarchy-ghtui #62 can copy it.

## Design

```mermaid
flowchart LR
  P[PipelinesPanel adopt()] -->|Model.barStatus| F[(status file)]
  F -->|FileView watch| W[bar widget, one per screen]
  W -->|click: omarchy-shell shell toggle| P
```

### The widget plugin

A new directory `bar-widget/` in this repo is a plugin of its own, id
`olafkfreund.gitlab-pipelines-bar`, installed beside the panel plugin:

- `bar-widget/manifest.json`:
  - `"kinds": ["bar-widget"]`, `"entryPoints": {"barWidget": "BarWidget.qml"}`.
  - `barWidget`: `displayName` "GitLab Pipelines", `category` "Development",
    `allowMultiple: false`, `defaultSection: "right"`.
  - `version` matches the panel's `manifest.json` (1.16.0).
  - No `keepLoaded`.

  This is the house pattern: `io.github.olafkfreund.nixi-button` is a
  widget-only plugin beside its overlay for the same reason (its manifest:
  "Omarchy gives a third-party plugin either a bar widget or an overlay,
  not both"). The panel plugin's manifest is unchanged, so enabling,
  disabling, Setup → Plugins and its `plugins[]` settings behave as today.
- `bar-widget/BarWidget.qml`:
  - **Base.** It extends `qs.Ui` `BarWidget`, with `moduleName` set to
    the id. Like gmessages' `BarWidget.qml`, it draws a
    `Ui.BarIconButton`, with the GitLab glyph `` (Nerd Fonts
    fa-gitlab) as an escape, and the counts as plain `Text` beside it.
    They sit in a `Row` on a horizontal bar and a `Column` on a vertical
    one (`vertical` from the base).
  - **Click.** `onPressed` runs `Quickshell.execDetached(["omarchy-shell",
    "shell", "toggle", "olafkfreund.gitlab-pipelines", "{}"])`, an argument
    list, not a shell string.
  - **Reading the status.** A `FileView` on the status file with
    `watchChanges: true` reloads it on change and parses it with
    `BarModel.view()`.
  - **Rate-limit expiry.** A one-shot `Timer` re-evaluates the view at
    `cooldownUntil`, so a rate-limit state clears by itself.
  - **Text.** All `Text` uses `Text.PlainText`. The tooltip goes through
    `BarIconButton.tooltipText`, which the bar draws as plain text (`Bar.qml`
    line 1858).
- `bar-widget/BarModel.js`: pure functions. The widget cannot import the
  panel's files: they are a different plugin directory.
  - `view(text, now)` → `{state, running, failed, label, tooltip,
    accessible, dimmed, urgent, recheckAt}`.
  - Unreadable, missing, or `version !== 1` text → state `none`.
  - Numbers are clamped to non-negative integers. `reason` is cut to 120
    characters.
- `bar-widget/LICENSE`: a copy of the root licence.

### The status file

- **Path:** `$XDG_RUNTIME_DIR/omarchy-gitlab-pipelines-status.json`.
  - Both sides read `XDG_RUNTIME_DIR` with `Quickshell.env`, and expose the
    path as a property so tests can point it elsewhere.
  - The runtime directory always exists, is private to the user (0700),
    and is emptied at logout, which suits status that must not outlive the
    session.
  - This changes the intent's suggestion of the state directory: that
    directory may not exist, QML cannot create it, and it would keep a
    stale status across reboots.
- **Shape**, written whole with `FileView.setText` and `atomicWrites: true`:

  ```json
  {"version":1,"instance":"<random>","host":"gitlab.com","state":"ok",
   "running":2,"failed":1,"countsAt":1795113908000,"cooldownUntil":0,
   "reason":"","writtenAt":1795113909000}
  ```

  `state` is `none`, `ok`, `stopped` or `rate`. The only free text is
  `reason`, which is the panel's own error string.

### The panel side

- **`Model.barCounts(repos)`** in `PipelinesModel.js` → `{running,
  failed}`. It skips archived, CI-disabled, blocked and errored projects.
  - `running` is the sum of `repo.active || 0`, as the project rows'
    "N running" shows.
  - `failed` counts projects where `latest(repo.runs)` (line 66) has
    `conclusion === "failed"`.
- **`Model.barStatus(polling, configError, host, instance, now)`** → the
  object above. The first matching rule wins:
  1. `stopped` with `reason`: a configuration error, `polling.auth` (the
     sign-in or setup stop, with `polling.error`), or `polling.catalogueError`.
  2. `rate` with `cooldownUntil = polling.cooldown`, when that is in the
     future.
  3. `none`, when `polling.countsAt` is unset.
  4. `ok`.

  The counts and `countsAt` are carried in every state. The merge-request
  view's `mrs.error` is never read.
- **`Polling.countsAt`**: a new field in `create()`, set to `now` in
  `activity()` (`Polling.js`, the function that stores a project's
  running pipelines; summaries call it too). `resetHost` leaves it unset.
- **Publishing** in `PipelinesPanel.qml`:
  - A `statusPath` property, a `statusInstance` set once at
    `Component.onCompleted` from `Date.now()` plus a random suffix, and
    `publishStatus()`.
  - `publishStatus()` writes only when the serialised object, without
    `writtenAt`, differs from the last one written.
  - It is called at the end of `adopt()`, which runs after every reply,
    open or closed (`receivePage`), so watch replies publish too.
  - It is also called in `configure()`'s `catch`, after setting `error`,
    and at `Component.onCompleted`. That first call writes `state: none`
    with the new instance, so a shell restart or plugin reload shows the
    no-data state.
  - A host change runs `resetHost` and then `adopt()`, so it publishes
    `none` for the new host.
- **The watch running-count fix** in `Polling.complete()`, `run` branch
  (lines 451-461). Before `mergeRuns`, note whether the cached run was
  `in_progress`. If it was, the resolved run is not, and
  `r.activeFromTotal` is set, then:

  ```js
  r.active = Math.max(running, (r.active || 0) - 1)
  ```

  The existing `Math.max(r.active, running)` stays for every other case.
  This applies open or closed; when open, the next activity read replaces
  it anyway.

### The widget's states

| State | Shows | Tooltip |
| --- | --- | --- |
| `none` | glyph, dimmed, no numbers | "GitLab Pipelines: open the panel to load" |
| `ok` | glyph; `● N` when running > 0; `✕ N` in the urgent colour when failed > 0 | "GitLab Pipelines · <host>", then "N running pipelines, N failed projects", then "Project counts from HH:MM; watched pipelines are live" |
| `stopped` | glyph and `!` in the urgent colour | "GitLab Pipelines stopped: <reason>. Open the panel to fix it." |
| `rate` (until `cooldownUntil`) | glyph, dimmed, last numbers | "GitLab paused until HH:MM", then the `ok` lines |

- The accessible name is the tooltip's lines joined with ", ".
- With no numbers to show in `ok`, the glyph shows alone.
- `HH:MM` uses the local time format.

### Packaging and docs

- **`flake.nix`:** a second package, `packages.<system>.bar`, copies
  `bar-widget/` (with `LICENSE`). `packages.default` stays the panel. The
  `checks.plugin` derivation also runs `node tests/bar.cjs`.
- **README**, new section "Bar widget":
  - What it shows and the two units.
  - Freshness: counts are as of the last project read; watches are live.
  - The states.
  - Install:
    - Git: link `bar-widget` as `~/.config/omarchy/plugins/olafkfreund.gitlab-pipelines-bar`,
      then `omarchy bar put olafkfreund.gitlab-pipelines-bar`.
    - Nix: the `bar` package.
    - nixarchy: a follow-up entry in nixarchy.
  - Known limits: the counts are stale while the panel is closed, and
    `failed` only covers pipelines the panel has seen.
  - "Refresh and errors" mentions the watch fix.
- **`manifest.json`:** 1.16.0. **`keybindings.sh`:** unchanged.

## Alternatives rejected

- **`bar-widget` + `service` kinds on the panel plugin (intent Q1 b):**
  - It changes `omarchy plugin enable` and Setup → Plugins for every user
    (`PluginRegistry.qml` lines 556-575, `shell.qml` lines 1965-1973).
  - The panel would have to read its settings from a bar entry too.
  - The kept service would survive a reload with stale counts.
  - A replacement bar would give the widget no service at all.
- **The widget walking host objects to reach the panel:** this is against
  the shell's documented API.
- **The state directory for the file:** it may not exist, QML cannot
  create it, and the status would outlive the session.
- **A Python helper call to write the file:** it costs a process per
  change; `FileView` already writes atomically (`shell.qml` lines 146-171).
- **Counting failed pipelines rather than projects:** that number grows
  with history.

## Risks

- **A second install step.** A user who installs only the panel has no
  widget. The README says so, and the widget appears in the bar's widget
  list only once its directory is installed.
- **Concurrent shells.** Two shells of one user, on two seats, would share
  the file. The `instance` field makes the last writer win, which is
  harmless.
- **`FileView` text caching:** it keeps old text when its file is emptied
  or deleted (the smoke-test memory). The panel never deletes the file and
  always writes whole objects, and tests use fresh file names.
- **The glyph** needs a Nerd Font, which Omarchy's bar font already is. A
  missing glyph shows a box.
- **Hosts:** p620 and razer on the 1.16.0 deploy; p510 is untouched.
  Placing the widget on p620 is a manual step for the owner.

## Verification

- `node tests/bar.cjs`, new, for `BarModel.view`:
  - every state;
  - bad or old-version text → `none`;
  - negative or non-integer numbers clamped;
  - a long `reason` cut;
  - `rate` turning into `ok` after `cooldownUntil`, via `recheckAt`;
  - tooltip and accessible text with singular and plural units;
  - zero counts showing the glyph only.
- `node tests/model.cjs`:
  - `barCounts` skips archived, disabled, blocked and errored projects;
  - `latest` failed versus a newer success;
  - `barStatus` precedence: config error, auth stop, catalogue error,
    rate, none, ok;
  - `mrs.error` ignored.
- `node tests/polling.cjs`:
  - `countsAt` is set by activity and summary but not by a `run` or job
    reply;
  - `resetHost` clears it;
  - the watch fix: an activity total of 1, then the watched run finishes
    while closed, gives `active` 0; with two running and one finishing it
    gives 1;
  - a non-total project is unchanged.
- `python3 -m unittest discover -s tests`: unchanged, still passes.
- QML smoke test, in the headless VM only:

  ```bash
  nix build ./ci#checks.x86_64-linux.qml-smoke -L --override-input gltui path:<worktree>
  ```

  - The panel writes `state: none` with an instance at start, then `ok`
    with counts after the fixture loads.
  - Writes are skipped when nothing changed.
  - A host change writes `none`, and a configuration error writes
    `stopped`.
  - The widget, loaded from `bar-widget/BarWidget.qml` with a fake `bar`
    object (horizontal, then vertical), shows the right label, colours
    and tooltip for each state from a written file.
  - A click runs the toggle command (captured through a fake
    `omarchy-shell` on `PATH`).
- `nix build .#bar` and `nix flake check`: the package holds
  `manifest.json`, `BarWidget.qml`, `BarModel.js` and `LICENSE`.
- Manual check on p620 after the deploy: link or install the widget, put
  it on the bar, and check its counts against the panel.
